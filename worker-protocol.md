# Протокол игрового исполнителя

`farm.py` ведёт очередь **собственных** аккаунтов. Имя аккаунта и игра хранятся в SQLite. Пароли и сеансы здесь не хранятся. Исполнитель задаётся владельцем фиксированной абсолютной командой в `farm_profiles.json`; модель Qwen не может запускать команды. Один процесс исполнителя получает JSON одной строкой на stdin:

```json
{"job_id": 1, "account_alias": "my-account-01", "game": "steal_egg", "target": 100, "private_server": null}
```

Он должен работать с уже авторизованным **собственным** аккаунтом в игровом клиенте, выполнить действия и проверить прогресс в игре. Он завершает работу с кодом 0 и печатает **только** JSON в stdout:

```json
{"observed_progress": 100, "account_alias": "my-account-01", "game": "steal_egg", "session_closed": true}
```

`session_closed: true` исполнитель возвращает только после фактического выхода из игрового аккаунта. При отсутствии подтверждения задача становится `failed`, даже если прогресс достиг цели. При ошибке исполнитель возвращает ненулевой код. Если прогресс вырос, но ниже цели, задача повторно попадает в очередь (не более 10 запусков); без роста прогресса она становится `failed`. Если достигнут и сеанс закрыт, становится `done`. Скрипт под конкретную игру и механизм чтения её прогресса нужно предоставить отдельно. Поля в JSON являются заявлением внешнего исполнителя, а не независимой проверкой Roblox. На Linux VPS без Roblox клиента `farm.py` только хранит и распределяет задачи. Не выдавайте аккаунт покупателю по одной лишь отметке `done`: результат исполнителя и доступ к аккаунту нужно проверить перед созданием лота.

Quick Login Roblox: новый клиент показывает код, уже авторизованное устройство подтверждает вход; по документации устройства должны быть рядом. Вход через почту требует подтверждённой почты и ввода кода на том же устройстве, где он запрошен. Ни один из этих способов не превращает код в безопасный постоянный токен для бота. QR и почтовый код нельзя передавать Qwen или хранить в журнале.

## Подарок после заказа

`bot.py` принимает от покупателя `/gift Ник friend` или `/gift Ник private https://www.roblox.com/…`. Для `friend` исполнитель отправляет заявку и ждёт принятия; для `private` входит в доступный приватный сервер. Поле `recipient` всегда проверяется перед передачей. Настройте в `catalog.json` точный товар и аккаунт продавца, добавьте его через `python farm.py add-account my-01 gag2_demo`. Команда игрового исполнителя получает JSON:

```json
{"operation":"gift","order_id":"F-42","account_alias":"my-01","game":"gag2_demo","item":"Енот","recipient":"BuyerName","method":"friend","server_url":null}
```

После **наблюдаемой передачи** исполнитель печатает один JSON и завершается с кодом 0:

```json
{"confirmed":true,"recipient":"BuyerName","item":"Енот","receipt":"game-confirmation-id"}
```

Для демонстрационной игры, которой вы владеете, пример серверного Luau находится в `roblox-demo/GiftService.luau`. Его нужно связать с реальной системой инвентаря и сохранением транзакций. Это не скрипт для чужого плейса: клиентские эксплойты и структура инвентаря там неизвестны. Бот не считает передачу успешной только по запуску скрипта.
